# Reproducibility guide

SUGAR separates reproducible offline computation from live-source collection. The canonical
Kyrgyzstan case uses checked-in source-derived fixtures and deterministic enrichment data; it does
not require credentials or network access. Live collection is an input-acquisition activity and
must be recorded separately from the analysis that follows.

## Five-minute offline verification

From a clean checkout, use a supported Python 3.11, 3.12, or 3.13 interpreter. The commands below
create an isolated environment, install the package, run the deterministic suite, and generate the
canonical case in a new directory:

```bash
python3.13 -m venv .venv
source .venv/bin/activate                 # Windows: .\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -e .
python -m pytest -m "not live"
python examples/cases/kyrgyzstan_2026/run_case.py \
  --output ./reproducible-output/kyrgyzstan-2026 \
  --clean
```

The case command prints a JSON summary. It should report 11 observations, 11 assessments, 12
structured activity locations, 11.0 total density weight, a passing record-integrity audit, a
conditional complete-package audit, and zero human-verified observations. The conditional status
is expected: the fixture deliberately carries an unresolved EducationUSA service-topology conflict
and must not silently adjudicate it.

The output directory is a complete ordinary SUGAR workspace. Its `sugar-project.json` and
`.sugar/workspace.sqlite3` record the project and artifact registry; the data, references, State
package, maps, and reports remain inspectable files. The generated maps and reports are not source
code inputs and should not be committed as if they were authoritative evidence.

## Dependency reproducibility

`pyproject.toml` declares the supported semantic dependency ranges. Release and CI installation
tracks use the checked-in hash-pinned files under `requirements/`:

| Track | Purpose |
| --- | --- |
| `runtime.txt` | newest compatible runtime resolution across supported Python versions |
| `runtime-min.txt` | Python 3.11 lowest-direct compatibility track |
| `release.txt` | build and SBOM tooling for tagged releases |

Use the appropriate lock for a release qualification run:

```bash
python -m pip install --require-hashes -r requirements/runtime.txt
python -m pip check
python -m pip_audit --format columns
```

Do not mix an editable install, an unpinned ad-hoc upgrade, and a release result. Record the
following with every externally shared result:

- SUGAR commit or release tag;
- Python version and operating system/architecture;
- lock file used and its SHA-256 digest;
- `python -m pip freeze` output, excluding credentials and private package indexes;
- command-line arguments and configuration with secret values removed;
- input-file checksums and research cutoff;
- output-file checksums.

For a compact runtime report, run:

```bash
sugar diagnostics --json
```

Diagnostics report versions, capabilities, and credential-presence booleans. They must never be
used as a substitute for recording the exact input files or for publishing private research data.
For support handoff, write the same redacted payload plus handling instructions as an atomic ZIP:

```bash
sugar diagnostics --bundle ./diagnostics.zip
```

Review the bundle before sharing it. It contains no workspace research files and is not a backup or
portable project archive; use the workspace archive workflow below when the project data itself must
be transferred.

## Determinism and live data

The offline case is deterministic in its checked-in inputs and model rules. Timestamps generated by
the workspace and artifact metadata are operational metadata, so they may differ between runs; the
case summary, findings, audit decisions, map counts, density conservation, and source/conflict
identities are the semantic outputs to compare.

Generated CSV/XLSX sidecars, harvest manifests, state snapshots, map metadata, and workspace
archives include a `runtime` object with the Python implementation, operating system, architecture,
and versions of SUGAR's declared runtime dependencies. Use those recorded versions when
investigating a mismatch; a missing optional package is recorded as `not-installed`. The runtime
record contains no credentials or source content.

Live collectors can change because platforms change content, pagination, availability, rate limits,
authentication requirements, and response fields. A live run must therefore preserve its raw
checkpoint/JSONL inputs, collection window, query or seed plan, access mode, collector version,
response status, and any deferred or inaccessible tasks before downstream normalization. A failed
or access-limited live run is not equivalent to an empty result.

Never put API keys, cookies, session tokens, private source material, or unredacted logs into a
reproducibility bundle. Follow [`SECURITY.md`](../SECURITY.md) and
[`legal-and-data-handling.md`](legal-and-data-handling.md).

## Artifact verification

A reproducibility check should validate both structure and semantics:

```bash
python -m pytest -m "not live"
python -m ruff check .
python -m ruff format --check .
python -m mypy
python -m pip_audit --format columns
python tools/check_release.py v1.2.0
```

For a scale qualification, use the offline stress harness. Keep the full SQLite checkpoint for
large runs and bound materialized export/map samples deliberately:

```bash
python tools/stress_test.py \
  --records 1000000 \
  --in-memory-sample 10000 \
  --skip-export --skip-map \
  --output-dir ./stress-output-1m
```

Compare elapsed time only on comparable hardware and runtime builds. Always compare row counts,
sample counts, artifact sizes, and `network: false` independently of wall-clock measurements.
See [`stress-testing.md`](stress-testing.md) for the scale plan and its limitations.

## Workspace transfer

Use the validated archive format when moving a project:

```bash
python -m sugar_core.workspace_cli archive PROJECT PROJECT.sugar.zip
python -m sugar_core.workspace_cli restore PROJECT.sugar.zip RESTORED-PROJECT
```

After restore, run `sugar-project status RESTORED-PROJECT --json`, compare the manifest project ID,
check missing artifacts, and rerun the relevant analysis from the restored inputs. External artifact
references remain explicit; an archive does not silently copy files outside the project root.

## What reproducibility does not prove

Reproducing an artifact proves that the checked-in code and supplied inputs produce that artifact.
It does not prove that a source was truthful, that a platform exposed its full population, that an
AI suggestion is correct, that geographic proximity implies overlap, or that any observation caused
an outcome. Evidence quality, source access, human review, and domain interpretation remain
separate gates.
